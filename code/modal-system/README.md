# Modal system

Two primitives — `ModalOverlay` and `ModalDialog` — that every modal in the app is built from, instead of each modal reimplementing teleport, transitions, escape-key handling, and outside-click detection on its own.

## How it works

`ModalOverlay` owns *lifecycle*: is it open, how does it close, what happens during the transition. `ModalDialog` owns *structure*: a required `title` prop, an optional content slot, a required actions slot, nothing else — no state, no teleport, no lifecycle of its own. Neither knows anything about what's actually inside; every consumer supplies a title string, an `isOpened` boolean, and whatever content and action controls it needs, and that's the entire contract.

Both are always imported through `index.js` — `import Modal from './modal-system'`, then `<Modal.Overlay>`/`<Modal.Dialog>` — never `fragments/ModalDialog.vue` or `fragments/ModalOverlay.vue` directly, which is also why both live under `fragments/`: the same "nothing outside the assembling file imports this directly" rule [`code-style/fragments-convention`](../../code-style/fragments-convention) documents for a fixed sequence of steps holds just as well here, even though these two aren't steps in a sequence — the folder now matches an invariant the barrel import was already enforcing. That's not a style preference: `ModalDialog` rendered on its own has no teleport, no backdrop, no escape or outside-click handling, no animation — it's inert markup, since every bit of that behavior lives in `ModalOverlay`. The two only do anything useful assembled together, which is why they're grouped and exported as a single namespaced object rather than as two independent components — the barrel import is what makes "always used together" something a consumer actually has to go along with, not just a note in a README they might not read. A project building a specific modal on top of these — a `UserModalDialog.vue` wrapping `Modal.Dialog` with its own content baked in, say — can name and shape that wrapper however its use case calls for; wherever it's actually rendered, though, it still has to sit inside `Modal.Overlay`. There's no version of `Modal.Dialog` that works standing alone, named component or not.

`ModalOverlay` renders through `<teleport to="body">`, which sidesteps the classic bug where a modal opened from inside a `transform`/`overflow: hidden` ancestor gets visually clipped or mis-positioned — the dialog is never actually a DOM descendant of wherever the trigger lives. That's also why the component opts out of Vue's automatic attribute fallthrough (`defineOptions({ inheritAttrs: false })`): fallthrough attributes are meant for a component with one clear root element to land on, and this one has neither — its content is teleported elsewhere, and what's teleported is two independently `v-if`'d, transitioning elements, not a single root Vue could reliably attach a stray attribute to.

`isOpened` drives two watchers, both `immediate: true` since a modal can mount already open (a route-driven modal, a confirm-before-leave dialog shown on load) and both behaviors need to apply from the first render, not just a later toggle: one locks/unlocks [`body-scroll-control`](../body-scroll-control) so the page can't scroll behind an open modal, the other adds/removes the `Escape` keydown listener that closes it. Both get an `onBeforeUnmount` safety net too — if the component is torn down while still open (a route change out from under an open modal, say), the scroll lock still gets released; the escape listener always gets removed regardless of `isOpened`, since it's only ever added while one isn't already attached.

`ModalOverlay` doesn't own its own open/closed state at all — `isOpened` is a prop the consumer controls, and the only way this component can ask for a close is by emitting `close`. Escape and an outside click both funnel through one internal function, `closeModal`, gated on `!isTransitioning && isOpened && !isCloseDisabled`, which is what actually emits it. Outside-click detection depends on `ModalDialog`'s root element stopping click propagation (`@click.stop`): the click-catching surface is the same full-screen wrapper the dialog renders inside, so without that `.stop`, a click on the dialog itself would bubble up and register as a click outside it.

A consumer's own action buttons are a different story: they're wired directly to the parent's `isOpened` ref (`@click="isOpened = false"` in `Example.vue`), not routed through `closeModal` at all. That means `isCloseDisabled` only blocks the two dismiss paths this component owns — Escape and outside click — and does nothing to stop a consumer's own action button from closing the modal mid-request; disabling that button for the same window is still the consumer's job. `isTransitioning` is covered next.

## How the opening and closing animation actually works

Both the backdrop and the dialog live inside their own `<transition>` — `modal-overlay` (opacity only) for the backdrop, `modal-dialog` (opacity plus a slight scale/translate) for the dialog — each wrapping a `v-if="isOpened"` div, rather than an always-mounted element that just toggles a class. That distinction matters: a `<transition>` around `v-if` is what guarantees the *leave* animation actually finishes before Vue removes the element, not just the *enter* animation on open. A modal that's meant to close with a fade-and-scale-down instead of vanishing mid-frame needs exactly that guarantee — a plain `v-if` with no `<transition>` would just remove the element the instant `isOpened` goes false. `appear` on both extends the same guarantee to a modal that mounts already open — without it, that first open would skip straight to the finished state instead of animating in. The two transitions are also deliberately independent rather than one shared block: the backdrop fading in slightly ahead of the dialog's fade+scale is what makes it read as one motion instead of two flat elements popping in at once.

Vue derives each transition's CSS class names from the `name` prop (`modal-overlay-enter-from`, `modal-dialog-enter-active`, and so on) and toggles them itself; they never appear as a literal `class="..."` string anywhere in the template for Tailwind's class scanner to pick up. That's why a small `<style>` block still exists in `ModalOverlay.vue` alongside the utility classes everywhere else — `@apply` is the supported way to hand a framework-generated selector a set of Tailwind values, and there isn't a way to express "style this dynamically-named class" as an inline utility instead.

The dialog transition's lifecycle hooks (`@before-enter`, `@before-leave`, `@after-enter`, `@after-leave`) drive `bodyInteractionControl.lock()`/`unlock()` from [`body-interaction-control`](../body-interaction-control), making the background `inert` for exactly the enter/leave window, not the whole time the modal is open — with its own `onBeforeUnmount` safety net too, same reasoning as the scroll lock above, in case the component is torn down mid-transition. The concrete failure this prevents: a dialog is technically in the DOM and clickable from its very first animation frame, not just once the animation finishes. If a trigger button and one of the dialog's own action buttons happen to land at roughly the same screen position — a "Delete" button opening a confirm modal whose "Confirm" button ends up right under the same cursor is the common case — an unlocked page lets that original click carry straight through onto the new button the moment it exists, before the user has actually seen it render. Locking interaction for the duration of the animation closes that gap in both directions: nothing under the dialog is clickable while it's still visibly in motion, whether it's opening or closing. This is also what `isTransitioning` (referenced in `closeModal`'s gate above) is actually for — the same window where interaction is locked is the window where closing is blocked, so a second Escape press or outside click mid-animation can't fire a close that's already in progress. That lock is scoped to the transition window only, though — once the dialog has finished animating in and is just sitting open, the background isn't `inert` anymore, so a keyboard user tabbing through the page at that point can still reach it. There's no focus trap keeping Tab cycling inside the dialog while it's open, and closing doesn't return focus to whatever triggered it either; [`body-scroll-control`](../body-scroll-control) still correctly stops the page from scrolling underneath at that point, it's specifically keyboard focus that isn't contained.

## Real, deliberate details worth knowing about

- **`isCloseDisabled`** blocks close while a request the modal depends on is still in flight — a consumer sets this while waiting on an endpoint to resolve. Without it, a user can dismiss the modal before that request settles, and its success/error handler ends up firing against a component that's already torn down its open context. It only covers Escape and outside click, though, as covered above — a consumer's own action buttons need their own disabled state for that same window.
- **`disableOutsideClick`** is an explicit escape hatch for modals that shouldn't be dismissible by accident — a multi-step flow, an in-progress destructive action, or any modal important enough that losing it to a stray outside click would be a real problem — off by default, opt-in per instance.

## Files

`fragments/ModalOverlay.vue` — lifecycle: teleport, transitions, escape key, outside click, interaction/scroll locking, all covered above. Structural and layout styling is inline Tailwind utility classes on the template; the one exception is the small `@apply`-based `<style>` block covering Vue's dynamically-named transition classes.

`fragments/ModalDialog.vue` — pure structure: a required `title` prop, an optional content slot, a required actions slot, no state of its own. Almost entirely inline Tailwind utility classes. The actions row uses `[&>button]:...` to size whatever the `actions` slot renders into a two-up row on larger screens — reaching past the slot boundary into whatever the caller renders, targeting the `button` element itself rather than a class so it isn't tied to any particular button component, though an action rendered as something other than a real `<button>` (a `RouterLink` styled to look like one, say) falls outside the rule and keeps its own intrinsic width instead of joining the layout. The one non-utility exception is a small scoped `<style>` block for the dialog's safe-area-aware bottom padding, `padding-bottom: max(1.5rem, env(safe-area-inset-bottom))` plus a legacy `-webkit-overflow-scrolling: touch` fallback for pre-iOS-13 Safari, inert on any current browser. Both are genuine CSS function expressions, not design-token values; wrapping a `max()`/`env()` call or an `@supports` condition in Tailwind's arbitrary-value brackets is technically possible but stops reading as a utility class the moment it does, so this one piece stays plain CSS rather than being forced into the inline-class shape everything else here uses.

`index.js` — the barrel both fragments are exported through (`Modal.Overlay`, `Modal.Dialog`); see above for why every consumer goes through it rather than importing either file directly. Per [`code-style/fragments-convention`](../../code-style/fragments-convention), it's the only file that imports anything from `fragments/`.

`Example.vue` — a button toggles `isOpened`, wrapping `Modal.Dialog`'s title/content/actions slots directly in `Modal.Overlay` with no component of its own in between.
