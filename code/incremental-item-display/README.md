# Incremental item display

A component that renders items in chunks as the user scrolls toward the end of what's currently rendered, instead of mounting every item — and every item's DOM, event listeners, and any nested components — all at once.

## How it works

An empty `<div aria-hidden="true">` — the sentinel — sits at the very end of the rendered list, present only while there's more to render. An `IntersectionObserver` watches it; the moment it scrolls into view (within `OBSERVER_OFFSET` px, so the next chunk starts rendering slightly *before* the user actually reaches the bottom, not exactly when they do), `renderVisibleChunks` bumps `renderedItemCount` by `chunkSize` and waits a tick. Since the sentinel is always the last element, growing the rendered count re-renders the list with the sentinel pushed further down — if the viewport is tall enough that the sentinel is *still* visible after one chunk, the `while` loop keeps rendering chunks (each followed by `await nextTick()` so the DOM actually updates and the sentinel's real position gets checked between iterations) until it either runs out of items or the sentinel finally scrolls out of view.

That `while` loop is the detail easy to get wrong: without it, a very tall viewport (a big monitor, browser zoomed out) could render exactly one chunk, see the sentinel still sitting in view, and never trigger a second one — `IntersectionObserver` only fires on a visibility *change*, not on "is still visible."

The rendered window also resets on its own whenever `items.length` changes: `renderedItemCount` snaps back to `chunkSize` and `renderVisibleChunks` runs again from there — which genuinely unmounts whatever was already rendered beyond that point (their `onUnmounted` hooks fire, any state they held is gone), not just scrolls the view back to it. That's the right behavior for "the whole list was refetched" — a new search, a different filter — where starting the window over from the top is exactly what should happen. It's a much rougher one for "a single item got appended to a list the user is already scrolled deep into": the same length-change watcher fires on that one-item arrival too, unmounting everything past the first `chunkSize` items for a change that, from the user's side, barely happened.

## Why nothing wraps the item

A semantic list implies its items are list-like content — text, links, simple values. What actually goes in the `item` slot is usually a self-contained composite widget with its own root element and its own semantics already: a card (often an `<article>`), a row, a whole sub-component. Wrapping that in `<li>` doesn't add meaning, it just puts a `listitem` role around something that already has its own identity, and forces every consumer into list semantics whether or not what they're rendering is actually a list — and even a neutral `<div>` still inserts a node the consumer never asked for, one that can throw off their own layout: a flex/grid gap counting it as an extra sibling, an `:nth-child` selector landing one element off, a parent combinator written assuming the item is a direct child of something specific.

So there's no wrapper at all — `v-for` sits on a `<template>` around the `<slot>`, not on a real element:

```
<template
    v-for="(item, index) in visibleItems"
    :key="itemKey ? String(item[itemKey]) : index"
>
    <slot 
        name="item" 
        :item="item" 
        :index="index"
    />
</template>
```

Vue's compiler recognizes that specific shape — a `<template v-for>` whose only child is a `<slot>` — and forwards the key as `renderSlot`'s own `branchKey` argument instead of trying to stamp it onto a DOM node. At runtime that value keys the `Fragment` `renderSlot` already builds to represent the slot's output, so it doesn't matter whether the consumer's `item` slot renders one root element or several — the whole group is keyed and diffed as a unit, and whatever the consumer writes in the slot is exactly what lands in the page, with nothing of this component's own standing in for it.

That specific shape is what makes the difference. Moving `v-for`/`:key` onto the `<slot>` tag itself still ends up keyed — Vue falls back to reading the key straight off `props.key` when no `branchKey` was forwarded — but that means `key` now travels inside the very props object handed to the consumer's scoped slot, so every `v-slot="{ item, index }"` destructure gets a stray `key` sitting alongside them: an internal keying value this component needed, leaked into a scope that was never meant to carry it. Keeping `v-for` on the `<template>` is what keeps that value out of props entirely — it only ever reaches `renderSlot` as `branchKey`, never something a consumer's slot template could see.

This component's job still stops at keeping items correctly ordered and keyed in the DOM, not at their appearance — and there's now nothing left to style even if it wanted to. How each item looks is entirely down to what the consumer puts in the slot.

## Why not just render everything

For a genuinely long list (hundreds+ items, especially with any per-item component logic — computed values, watchers, nested slots), mounting all of it at once is real, measurable main-thread work up front, blocking interaction while it happens. Chunked rendering spreads that cost across scroll instead of paying it all at mount. It's a much smaller change than true virtualization (which also *unmounts* off-screen items as they scroll past) — appropriate when the honest expectation is "a few hundred items, rendered progressively" rather than "tens of thousands, most never seen." Scrolling further never unmounts anything already rendered — `renderedItemCount` only ever grows through that path — so scroll through a 2,000-item list whose own length stays put and all 2,000 end up mounted eventually, spread out over time instead of paid for at once. That guarantee is specifically about scrolling, though: it's the source list's own length changing, not scrolling, that resets the window and unmounts the tail, as covered above — so it doesn't hold across a list that's actively growing or shrinking while the user is in it. For a list large enough that even the steady, spread-out version of this cost matters, true virtualization — only ever mounting what's currently in the viewport, unmounting what scrolls away — is the correct tool; this technique only defers the *initial* render cost under a stable list, it doesn't cap sustained memory or DOM-node growth.

## About: `maxHeightClassName`

Passing `maxHeightClassName` wraps the list in its own scroll boundary: capped to whatever height that class establishes, scrolling internally past it, with `pr-2`/`-mr-2` — a matched padding-right and negative margin-right — reserving room for the scrollbar so it doesn't narrow the content column the moment one appears. The prop is typed as [`shared-types`](../shared-types)'s `ClassName` — anything Vue's own `class` binding accepts: a single class, an array, or an object of class -> boolean — and applies it straight onto the same element as those fixed scrollbar-gutter classes, so a caller reaches for Tailwind's own responsive and conditional class syntax (`max-h-64 md:max-h-96`, `{ 'max-h-[420px]': isCompact }`) instead of this component inventing its own mechanism for the same thing. A class assembled by interpolating a runtime-computed number (`` `max-h-[${px}px]` ``) won't work — Tailwind only generates CSS for class names its build-time scanner can find as literal text somewhere in the caller's own source, and a computed string never appears there — but every class or class expression written out literally, including inside a conditional object or array, does, since the literal text is what the scanner is actually looking for. `IntersectionObserver`'s `root` follows automatically — once `maxHeightClassName` is set, the `scrollableElRoot` computed swaps the observer's root from the default (the browser viewport) to this element itself, so the sentinel's visibility is measured against the list's own scroll box, not the page's.

That's a self-contained alternative to measuring against a container the caller supplies: the alternative has to assume whatever renders directly around the list *is* the scroll boundary — a spacer element, an extra wrapper, and the assumption breaks silently with no error to point at. Because the boundary here is whatever this component renders itself, there's nothing left for a caller to get wrong. The trade-off is the flip side of that same self-containment: a list that genuinely needs to scroll inside an ancestor this component doesn't create — a scroll region built some other way — has no prop for that; `maxHeightClassName` only covers a boundary this component owns. It also means there's no path left for a height that's genuinely computed at runtime with no class behind it at all — matching another element's measured height in JS, say — since detecting the scroll boundary (`maxHeightClassName !== undefined`) and setting it now happen through the same single prop rather than a value and a separate flag; that's a deliberate trade against carrying two props to cover a case nothing here currently needs.

The scrolling box and the sentinel's positioning context are deliberately two separate elements, not one. The sentinel is positioned `absolute`/`bottom-0` against its immediate parent, and that only tracks "after the last item" if that parent grows freely with its content; an `overflow-y-auto` box's own height stays fixed at whatever `maxHeightClassName` sets regardless of content, so putting the sentinel directly inside the scrolling box would glue it to the visible bottom of the scroll port instead of the actual end of the list — always "visible," never actually signaling anything.

That positioning-context element always keeps its own `relative`, since that's what the sentinel's `absolute` positioning depends on; `listClassName` only ever appends alongside it, never replaces it. It takes the same class-value shape as `maxHeightClassName` — a string, an array, or a conditional object — for the same reason: a caller styling this wrapper is just as likely to need a responsive or conditional class here as on the scroll boundary. It's also deliberately never handed to `IntersectionObserver` as `root`, even on the branch where there's no `scrollRootRef` to use instead — an explicit `root` only gets clipped to what's actually on screen when that element clips its own overflow, and this element never does; it has to keep growing freely with content for the reason above. Handing it to `root` would make the sentinel register as intersecting the instant it exists, no matter how far down an unscrolled page it actually sits — confirmed by pointing a real `IntersectionObserver` at a non-clipping ancestor: `isIntersecting` came back `true` with a full `1.000` ratio for a sentinel sitting 10,000px below the fold, on the very first callback. `root` stays `null` — the real browser viewport — on that branch, because nothing else in this component is actually clipped to the visible screen.
